## The OAuth cookie hunt — root cause in one sentence

**The browser-side Supabase client was constructed with
`@supabase/supabase-js createClient` (defaults to localStorage + implicit
OAuth) while the server middleware used `@supabase/ssr createServerClient`
(reads cookies + expects PKCE).** Two incompatible OAuth flows side by
side. OAuth succeeded client-side, localStorage got the session, the
server never saw a single `sb-*` cookie, every protected route bounced
to /login.

### The red herrings (what we tried first and why they didn't fix it)

1. **Vercel domain + cert** (`462…fix` already from yesterday) — needed
   for the domain to respond at all, but unrelated to sessions.
2. **038 creators insert RLS** — also already done yesterday; unblocks
   project INSERT, not the OAuth flow itself.
3. **Supabase "Additional Redirect URLs" whitelist** — user had bare
   hosts, needed `/**` wildcards. Added those. OAuth server-side started
   creating users (confirmed via Supabase Auth dashboard). But browser
   still saw no cookies. So this was necessary but not sufficient.
4. **Supabase "Allow users without an email" toggle** — enabled in case
   GitHub returned no email. Irrelevant for us but closed a plausible
   theory.
5. **`cookieStore.set()` vs `response.cookies.set()` in /auth/callback**
   (commit `a0f7c40`) — legitimately correct fix for Next 15 Route
   Handler cookie semantics, but immaterial because the callback was
   never being hit with a code.
6. **`getUser()` → `getClaims()` in middleware** (commit `e74b931`) —
   also a correct fix per the canonical Supabase example ("users may
   be randomly logged out" warning), but again immaterial: no session
   cookies means `getClaims` returns null either way.

### The actual fix (commit `e418a7c`, one file, 20 lines)

`lib/supabase.ts`:

```ts
// BEFORE
import { createClient } from "@supabase/supabase-js";
export const supabase = createClient(supabaseUrl, supabaseAnonKey);

// AFTER
import { createBrowserClient } from "@supabase/ssr";
export const supabase = createBrowserClient(supabaseUrl, supabaseAnonKey);
```

`createBrowserClient` uses **cookies + PKCE** — same storage medium
the server middleware reads from. After this, OAuth lands on
`/auth/callback?code=...`, our handler exchanges the code, the cookies
get set, middleware sees them on the next request. /launch works.

### How we got to the answer

The breakthrough was the user screenshotting Chrome devtools → Application
tab and showing `Cookies` was empty except for a PostHog cookie, while
the welcome banner on /home said `@ALEX-JB`. If the client thinks it's
logged in but the server sees no cookies, those two systems are using
different storage. Grepping `lib/supabase.ts` immediately surfaced the
wrong package import.

### Lesson

When an app uses both `@supabase/ssr` AND `@supabase/supabase-js`, the
BROWSER client must come from `@supabase/ssr` (`createBrowserClient`),
not `@supabase/supabase-js` (`createClient`). Otherwise storage types
diverge. The Supabase docs mention this but it's buried under a
framework selector and easy to miss.

## Claude AI Review integration (commit `7e28fb0`)

With auth unblocked, pivoted to replacing the hand-written stub in
`lib/ai.ts generateStructuredReview` with real Claude calls:

- **SDK**: `@anthropic-ai/sdk` (was already a dep from earlier scaffolding)
- **Model**: `claude-sonnet-4-6`
- **Structured output**: tool_use with forced `tool_choice`, so the
  response is always valid JSON matching `StructuredReview` (5-7 actions
  with type/severity/rationale/candidates/success_metric + 5 aggregate
  scores). No prose-parsing, no JSON.parse-of-markdown.
- **System prompt**: "VibeX Launch Coach" voice — YC-partner directness,
  name the specific problem, hand over usable rewrites not vague advice.
- **Fallback**: when `ANTHROPIC_API_KEY` isn't set OR the call throws,
  fall through to the original hand-written stub. UI never breaks.
- **Secondary fix in same commit**: the `stubReview()` helper in both
  launch-feedback route handlers was looking up projects in mock-data
  only, so any real `proj-xxx` id got "Project not found" 404. Changed
  to query Supabase first, fall through to mock only as a last resort.
